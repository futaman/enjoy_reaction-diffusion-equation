# インタラクティブ学習ドリル 汎用仕様

「触って確かめながら学ぶ、HTML 1ファイルのドリル」を作るための、**テーマに依存しない仕様**です。
このリポジトリ（反応拡散方程式）は、この仕様の最初の適用例です。別のテーマで作るときは、この文書に従い、§10 のひな形を埋めて、そのテーマの仕様書を作ってください。

| 文書 | 役割 |
|---|---|
| この文書 | どのテーマでも共通の決まり |
| [spec.md](spec.md) | 反応拡散ドリル固有の仕様（適用例） |
| [design.md](design.md) | 反応拡散ドリルの雰囲気（§4 の具体例） |
| [teaching-materials.md](teaching-materials.md) | 反応拡散ドリルの材料集（§2 の具体例） |
| [chapter-guide.md](chapter-guide.md) | 反応拡散ドリルの章の書き方（§5 の API の具体例） |

## 1. 前提を決める

作り始める前に、次の5つを決めて仕様書の最初に書きます。あとで迷ったら、ここに立ち返ります。

| 項目 | 決めること | 例（反応拡散） |
|---|---|---|
| 学習者 | 今の知識。どこまでは知っていて、どこからは知らないか | 中学数学。微分は「何となく」 |
| ゴール | 終わったときに**自分で何ができるか**。「わかる」ではなく、行動で書く | 狙った模様を自分で作れる |
| 使い方 | 先生と一緒か、一人か。両方なら両方に対応する | 先生が横につく。一人でも進められる |
| 数式・専門用語の深さ | どこまで本物の記号を使うか | ∂ や ∇² も使う。マス目の計算と対応させる |
| 範囲 | やること・やらないこと | 式の改造はしない |

## 2. 教材設計

### 2.1 材料を先に洗い出す

章を書く前に、次の3種類の材料に ID を付けて一覧にします。章はこの ID を参照して組み立てます（材料集 → 章への割り当て、の順）。

| 種類 | ID | 中身 |
|---|---|---|
| つまずき | T01… | 学習者が誤解しやすい点。「起きがちな誤解」と「対策」をセットで書く |
| たとえ | A01… | 説明に使うたとえ話。「長所」と「限界」をセットで書く |
| 仕掛け | M01… | ドリルの部品・手法（予想→観察、1マスの家計簿、わざと壊す など） |

- 特に大事なつまずきには ★ を付けて、「重点」としてドリルで正面から扱います。
- ★ のつまずきが、どの章で扱われているかを必ず確認します（扱っていない ★ を残さない）。

### 2.2 メインのたとえは1つに絞る

- 教材全体を通すたとえ（キャラクター設定）を1つ決め、最後まで崩しません。例：草（u）とウサギ（v）。
- たとえが合わない所では、別のたとえに**切り替えると明言**します。例：「ここだけ水槽のかけ流しで考えます」
- 動機づけの話題（歴史、身近な実例、研究の話）も、材料として集めておきます。

### 2.3 章の並べ方

| 段階 | 役割 | 例（反応拡散） |
|---|---|---|
| プロローグ | 完成形を見せて「やってみたい」を作る。問題は出さない | 動く模様、チューリングの話 |
| 積み上げ | 1章に新しい考えは1つだけ。記号はその章で初めて出す | 変化の速さ → ∂u/∂t → 拡散 → ∇² → 反応 |
| 謎の提示 | 「直感と違う結果」を見せて、答えを先の章に持ち越す | 拡散だけでは模様が消える。なぜ模様が？ |
| 統合 | 部品を組み合わせ、手計算とコンピュータが一致することを確かめる | 1マスを手で1コマ進める |
| 謎の回収と応用 | 謎に答え、狙った結果を自分で出す | 模様の地図、再現チャレンジ |
| 自由ラボ | クリア条件なしで自由に作る | 種を描く、色、保存 |

### 2.4 1章の組み立て

すべての章は、同じ順番で並べます。

1. 章番号、タイトル、**この章のねらい**（1行）、クリアまでの進み具合
2. ステップの積み重ね：解説 → デモ → 問題
3. 次の章への橋渡し（1〜2行）
4. 先生用メモ（折りたたみ）：扱うつまずき ID、問いかけの例、よくある反応
5. 前へ / もくじ / 次へ

### 2.5 問題

| 種類 | 使いどころ |
|---|---|
| 選択 | 意味や理由を問う。誤答の選択肢には、つまずき（T）を仕込む |
| 予想→観察 | 動かす前に予想させる。外れても失敗にしない。観察したら正解扱い |
| 数値 | 手計算。全角数字や「−」も受け付ける。許容誤差を決めておく |
| マス入力 | 地図や表の形で計算させる |
| 対応づけ | 記号と意味、形と性質を結ぶ |
| 穴埋め | 長い計算を段階に分ける |
| チャレンジ | 「この結果を自分で出せ」。合格条件を機械的に判定する |

- **誤答ごとに理由を返します。** 「ちがいます」だけで終わらせません。
- **ヒントは3段階**：考え方の向き → 途中の式 → 答えの手前。最後に「答えを見る」を置きます。
- **クリア条件：** 正解数で決めるのが基本です。特定の問題を必ず解かせたいときは、問題の ID で判定し、何が残っているかを表示します。予想問題は見るだけでクリアになるので、予想問題だけでクリアできないようにします。
- 問題の ID はあとから変えません（進み具合の記録に使うため）。

## 3. 言葉づかい

- 学習者に、となりで話しかける調子で書きます（日本語なら です・ます調）。
- 1段落は2〜3文まで。難しい言葉は、すぐ後ろで言い換えます。
- 記号には読み方を添えます。
- **画面の位置に頼る言い方をしません**（「右のデモ」「下の表」など）。PC とスマホで並び方が変わるためです。名前で呼びます（「草原の家計簿」「🧮 電卓ボタン」）。
- 本文に書く数値や主張は、すべてシミュレーションやテストで確かめてから書きます（§7）。
- フィードバックの言い方：

| 場面 | 言い方 |
|---|---|
| 正解 | 短く祝って、すぐ「なぜ正しいか」 |
| まちがい | 責めずに、その選択肢がなぜ違うか |
| おしい | 違う所を指さす（例：「＋と−を確認しましょう」） |
| 予想が外れた | 「予想してから見ることが大事です」 |
| クリア | 一度だけ、控えめに（✓ と短い通知） |

## 4. 見た目と雰囲気

### 4.1 原則

- 雰囲気をひとことで決めて、文書に残します（例：「先生が方眼ノートに描いてくれる、ていねいな説明」）。
- 落ち着いた見た目にし、主役は**動くデモと、自分で計算した数字**にします。
- 色・余白・角丸・影は、デザイントークン（CSS 変数）で一か所にまとめます。

### 4.2 色の決まり

- 役割ごとに色を決めます：背景、カード、文字（3段階）、線、アクセント、正解、まちがい、ヒント、先生用。
- **大事な概念ごとに固定の色を決め、本文・式・図・表のすべてで同じ色を使います。** 色を見ただけで、どの概念の話かわかることが目標です。例：式の4つの項に青・緑・オレンジ・紫。
- 「量」と「変化」のように混同しやすいものは、色で区別します。
- 新しい色を足すときは、既存の役割の色と紛らわしくないか確認します。
- 色だけに頼らず、文字や記号（✓、＋/−）でも伝えます。
- 色で値を表す図には、必ずカラーバーと「色が何を表すか」を付けます。色覚に配慮したパレットを選べるようにします。
- 明るい表示と暗い表示の両方に対応します。

### 4.3 囲みの使い分け

| 囲み | 使いどころ |
|---|---|
| ポイント | 覚えてほしい1文 |
| お話 | たとえ話、歴史の話 |
| 注意 | よくあるまちがい、壊れる条件 |
| 謎 | 次の章へ持ち越す問い |
| もっと詳しく（折りたたみ） | 厳密な話、補足。先生がいるときは閉じたままでよい |
| 先生用メモ（折りたたみ） | 教える人向け |

### 4.4 動き

- デモは開いた瞬間から動いているか、▶ ひとつで動くようにします。
- 再生バーの並びは全デモで同じにします：再生 / 1コマ進める / はじめから / 速さ。
- **1コマ送りを必ず用意します。** 速い変化を止めて、数字と見比べられるようにするためです。
- 図のどこをクリックしても、その場所の値が見られるようにします。
- わざと壊すデモは、必ず「はじめから」で戻れるようにします。
- 動くのはデモだけです。画面の演出（フェード、バウンドなど）は付けません。

### 4.5 ゲームっぽさの度合い

| 入れる | 入れない |
|---|---|
| 章ごとのクリア ✓ と進み具合 | 点数、ランキング、制限時間 |
| 「つづきから」 | 効果音、紙吹雪 |
| コレクション（未獲得は「？」で見せる） | クリアしないと先に進めない仕組み |

## 5. 技術

### 5.1 配布形態

- **HTML ファイル1つ**。CSS と JavaScript は埋め込み、外部のライブラリ・フォント・画像は読み込みません。
- オフラインで動き、メールや USB で渡せます。GitHub Pages などで公開することもできます。
- 目安の大きさは 500KB 以内。事前に計算したデータを埋め込むときも、大きさを確認します。
- 対象ブラウザは、最近の Chrome / Edge / Safari / Firefox です。

### 5.2 作り方

- 開発中はファイルを分け、ビルドで1つにまとめます。
- ビルドには、出力先と含める章を選べるオプションを付けます（複数人が同時に作業してもぶつからないように）。

```
src/
  index.template.html   シェル
  styles/base.css       デザイントークンと共通の見た目
  core/                 共通部品（テーマに依らないものと、テーマ固有のエンジン）
  chapters/             1章1ファイル。registerChapter() で登録
tests/                  数値の検算（Node）とブラウザでの確認（Playwright）
tools/                  パラメータ検証などのスクリプト
docs/                   仕様書類
dist/index.html         配布物
```

### 5.3 共通部品

**テーマに依らない部品**（別のテーマでもそのまま使える）

| 部品 | 役割 |
|---|---|
| DOM ヘルパー | 要素を作る、段落、囲み、もっと詳しく、先生用メモ、ステップ（2カラム） |
| 操作部品 | ボタン、つまみ、切り替え、セグメント、数字のマス |
| 問題 | §2.5 の各種類、3段階ヒント、答えを見る、誤答の理由 |
| 再生バー | 再生 / 1コマ / はじめから / 速さ、条件で止める、画面外で止める |
| グラフ | 棒グラフ、時間グラフ（表示幅 × 画素密度で描く） |
| 電卓 | 四則演算とかっこ（eval を使わない） |
| 保存 | 進み具合、コレクション、設定。保存できない環境でも動く |
| アプリ | 章の登録、ルーター、トップページ、章の枠、クリア判定、テーマ切り替え |

**テーマ固有の部品**（テーマごとに作り直す）

| 部品 | 例（反応拡散） |
|---|---|
| エンジン | 反応拡散のシミュレーション。DOM に触らず、Node でもテストできるようにする |
| 表示 | 草原ビュー（2次元の値を色で表示） |
| 内訳表 | 1マスの家計簿（各項の値と次の値） |
| 色分けした式 | 項をクリックしてオン・オフ |
| プリセット | 模様のパラメータと合格範囲 |

### 5.4 実装の約束

- **キャンバスは表示幅 × 画素密度で描きます。** 内部の幅を固定すると、スマホで文字が読めなくなります。表示幅が変わったら描き直します。
- **スクロールを妨げません。** `touch-action: none` は、指で描くキャンバスだけに付けます。
- テーマを切り替えたら、独自に描いた図も描き直します（切り替えのイベントを流す）。
- 1ページに重いデモを置きすぎません。画面外のデモは止めます。重い計算は数フレームに分け、ページを固めません。
- 横幅 360px で横スクロールが出ないようにします。ボタンは指で押しやすい大きさにします。
- キーボードでも操作できるようにし、動きを減らす設定の端末に配慮します。
- 保存（localStorage）は失敗しても動くようにします。保存はそのブラウザとファイルの場所に結びつく、ということを利用者向けの説明に書きます。

## 6. 数値シミュレーションを使うときの約束

- 手計算とシミュレーションで、**まったく同じ定義と計算**を使います。手で計算した答えが、コンピュータの答えと一致することが、教材の説得力になります。
- 教材向けに定義を簡単にした場合（例：∇² を「まわりの平均 − 自分」にする）は、本来の定義との違いを「もっと詳しく」で正直に書きます。
- **安定条件には余裕を持たせます。** 境目ちょうどの値は使いません。例：D × Δt = 1 ちょうどは壊れるので、Δt = 0.8。
- プリセットの値や合格範囲は、文献の値をそのまま使わず、教材と同じ計算で検証してから確定します。検証のスクリプトとレポートを残します。
- 「〜すると〜になる」という本文の主張は、すべてテストで確かめます。

## 7. 品質の確かめ方

| 確かめること | 方法 |
|---|---|
| 問題の正解、本文の数値 | Node のテスト（エンジンで検算）。答えは章のデータから読み、問題文と同じ値を使う |
| 本文の主張（〜すると〜になる） | Node のテストで実際に計算する |
| エラー、横はみ出し | ブラウザで全ページを PC 幅と 360px で開く（スモークテスト） |
| 見た目 | スクリーンショットを**人の目で見る**。暗い表示でも確認する |
| 操作 | 全部のボタン、ヒント、問題を実際に押す |
| 単体で動くか | ネットを切って全ページを開く。外部への通信が 0 件であること |
| 章をまたいだ一貫性 | 書いた人とは別の人が、通しで点検する（§7.1） |

### 7.1 通し点検の観点

複数の人で章を書いた場合は、必ず別の人が最初から最後まで通して点検します。

1. **正しさ：** 計算のまちがい、問題の答え、本文とシミュレーションの食い違い
2. **章をまたいだ一貫性：**
   - 記号と呼び名がそろっているか（Δt と dt、F と k の名前など）
   - 色の決まりが守られているか
   - 「第N章で学んだ」の参照先が正しいか
   - 記号を導入前に使っていないか
   - 前の章で教えたことと矛盾していないか（例：「消える」と「うすく広がる」）
   - 謎の提示と回収がつながっているか
3. **学習者の流れ：** 急な飛躍、説明のない言葉、必要な情報がまだ出ていない問題、多すぎる/少なすぎるヒント、達成できない/簡単すぎるクリア条件、位置に頼る言い方
4. **動作：** エラー、固まり、はみ出し、文字の切れ、暗い表示での読みにくさ

指摘は「重要度（高/中/低）・場所・問題・直し方」の表で残し、高から直します。

## 8. 進め方

| フェーズ | 内容 |
|---|---|
| 0. 前提 | §1 を決める |
| 1. 材料 | つまずき・たとえ・仕掛けを洗い出す（§2.1）。メインのたとえを決める |
| 2. 仕様 | 章への割り当て、雰囲気、技術を仕様書にまとめる |
| 3. 土台 | 共通部品とプロローグ（章のお手本）を作る。並行して、パラメータを検証する |
| 4. 章 | 章ごとに並行して作る。各章は自分のファイルだけを書く |
| 5. 点検 | 通し点検（§7.1）をして、指摘を直す |
| 6. 公開 | 単体で動くことを確かめ、配布・公開する |

- **ファイルの持ち主を決めます。** 章の担当は自分の章とテストだけを書き、共通部品の変更は統括が引き取ります。担当から出た共通部品への要望は、他の担当にも知らせます。
- 共通部品の使い方は「章を書くための手引き」にまとめ、変更のたびに更新します。
- 仕様と実装が食い違ったら、どちらが正しいかを確かめてから、仕様書も直します。
- 公開は、main に push するとテスト → ビルド → 公開まで自動で動くようにします（例：GitHub Actions と GitHub Pages）。

## 9. 完成の定義

- [ ] ★ のつまずきが、すべてどこかの章で扱われている
- [ ] すべての章に、ねらい・デモ・問題・クリア条件・橋渡し・先生用メモがある
- [ ] すべての数値問題に、3段階のヒントと「答えを見る」がある
- [ ] すべての誤答に理由がある
- [ ] 問題の正解と本文の主張が、テストで検算されている
- [ ] 全ページで、PC 幅・360px ともにエラー 0 件、横はみ出し 0 件
- [ ] 明るい表示・暗い表示の両方で、文字と図が読める
- [ ] ネットを切っても全ページが動く
- [ ] 通し点検の高・中の指摘がすべて直っている
- [ ] 位置に頼る言い方がない

## 10. 新しいテーマの仕様書のひな形

新しいテーマで作るときは、次の項目を埋めた `spec.md` を作ります。

```markdown
# 〈テーマ〉ドリル 仕様書

## 1. 決定事項
| 項目 | 決定 |
|---|---|
| 対象 | |
| ゴール（自分で何ができるようになるか） | |
| 使い方（先生と / 一人で） | |
| 数式・専門用語の深さ | |
| 扱うモデル・題材 | |
| メインのたとえ | |
| 範囲（やらないこと） | |
| 雰囲気（ひとことで） | |
| 重点（★のつまずき） | |

## 2. ゴールの式・ゴールの姿
（最後に読める・作れるようになるもの。概念ごとの色の割り当て）

## 3. 章構成
| 章 | テーマ | 新しく出る記号 | 扱うつまずき | 主なデモ | ドリルの例 | クリア条件 |
|---|---|---|---|---|---|---|

（章ごとに：ねらい / つまずき / たとえ / 仕掛け / デモ / ドリル / クリア / 先生用メモ）

## 4. テーマ固有の部品
（エンジン、表示、内訳表、プリセット）

## 5. 検証が必要な値
（文献の値の候補。教材と同じ計算で確かめて確定する）

## 6. 未決事項
```

あわせて、`teaching-materials.md`（T / A / M の材料集）と `design.md`（雰囲気の具体化）も作ります。

### 10.1 このリポジトリから持ち出せるもの

| そのまま使える | テーマに合わせて作り直す |
|---|---|
